ONVIF에서 HTTPS 인증서를 바꾸는 기능을 구현하려고 했다. 장치에는 이미 HTTPS 서버가 있었고 인증서를 생성하고 읽는 코드도 있었다. 처음에는 ONVIF 요청을 받아 기존 인증서 함수에 연결하면 될 것 같았다.

그런데 기존 코드를 따라가 보니 인증서 한 쌍을 사용하는 것과 여러 인증서를 관리하는 것은 차이가 컸다. 새 인증서를 추가했을 때 기존 인증서를 어떻게 구분할지, HTTPS가 사용 중인 인증서를 지워도 되는지부터 정해야 했다.

그래서 첫 작업은 KeyStore로 잡았다. 이 글은 2026년 9월에 진행한 AdvancedSecurity 구현 중 저장소 기반을 만드는 단계까지 다룬다. nginx 연동과 ONVIF API 연결은 그다음에 진행했다.

## HTTPS가 되는데 무엇을 더 만들어야 했나

HTTPS 서버를 실행하려면 서버가 사용할 인증서와 개인키가 필요하다. 기존 구현은 정해진 디렉터리에서 인증서와 키 파일을 찾아 웹 서버에 넘기는 방식이었다.

ONVIF로 인증서를 관리하려면 클라이언트가 특정 인증서를 지목할 수 있어야 한다. 인증서를 추가한 뒤 목록을 조회하고, 그중 하나를 HTTPS에 할당하고, 더 이상 쓰지 않는 인증서는 삭제하는 흐름이다. 파일이 존재하는지만 확인해서는 이 흐름을 처리하기 어렵다.

| 기존에 하던 일 | 새로 필요해진 일 |
| --- | --- |
| 인증서와 키 파일을 찾는다 | 여러 객체를 ID로 구분해 조회한다 |
| 사용할 파일을 웹 서버에 넘긴다 | 저장된 객체와 실제 사용 중인 객체를 구분한다 |
| 인증서 파일을 삭제한다 | 사용처를 확인하고 삭제 가능한 객체만 지운다 |
| 부팅할 때 파일을 다시 읽는다 | 객체 ID와 사용처 관계까지 복원한다 |

ONVIF Security Service 26.06도 Keystore와 TLS Server를 별도 절로 정의한다. 저장소의 객체 관리와 TLS 서버에 인증서를 할당하는 동작을 나눠 볼 수 있다. 이 연재에서는 코드와 namespace에서 익숙한 AdvancedSecurity라는 이름을 사용한다. [Security Service 26.06 §5.2·§5.3](https://www.onvif.org/specs/2606/ONVIF-Security-Service-Spec-v2606.pdf)

당장은 이 중 저장소 쪽이 필요했다. 인증서를 구분하고 보관하는 규칙이 있어야 nginx와 ONVIF도 같은 대상을 가리킬 수 있었다.

## 1. 기존 인증서 코드는 어디까지 재사용했나

기존 인증서 모듈에는 생성과 읽기 기능이 있었다. 다만 인증서와 개인키를 각각 파일 확장자로 찾고, 삭제도 특정 ID를 대상으로 하는 구조가 아니었다. 이 코드에 목록 조회와 참조 검사까지 계속 붙이면 기존 사용처의 동작도 함께 바뀔 수 있었다.

기존 모듈은 유지하고 공통 KeyStore를 추가했다. 기존 인증서를 저장소로 가져오는 연결점도 마련했다. 처음부터 웹 서버와 ONVIF까지 한 번에 바꾸지는 않았다.

첫 구현에서 저장소가 맡은 일은 다음과 같다.

- 인증서와 개인키를 등록하고 ID 발급
- ID로 객체 조회, 목록 조회, 개별 삭제
- 사용처 참조 등록과 해제
- 디스크 저장과 초기화 시 복원

여기에는 SOAP 응답 생성이나 nginx 재기동 코드를 넣지 않았다. 예를 들어 인증서를 삭제하는 ONVIF 요청을 받더라도, 삭제 가능 여부는 저장소가 판단하도록 했다. 같은 인증서를 웹 화면에서 삭제할 때도 같은 규칙을 적용할 수 있기 때문이다.

기존 보안 빌드의 저장용 키 관리 코드를 재사용하는 방향도 검토했다. 하지만 그 변경이 기존 빌드까지 건드리는 문제가 있어 되돌렸고, 첫 구현의 적용 범위는 일반 펌웨어로 제한했다. 저장소를 연결하는 작업과 기존 보안 빌드의 키 관리 변경을 함께 진행하지 않기로 한 것이다.

## 2. 인증서가 있다는 것과 사용 중이라는 것을 구분했다

인증서가 두 개 있다고 해서 HTTPS 서버가 두 개를 모두 사용하는 것은 아니다. 갱신용 인증서를 미리 등록해 둘 수도 있고, 기존 인증서를 보관한 채 새 인증서로 바꿀 수도 있다.

그래서 객체 정보와 사용처 참조를 따로 관리했다. 아래 ID는 관계를 설명하기 위한 예시다.

```text
저장된 객체
  cert_a: 기존 인증서와 개인키
  cert_b: 새로 등록한 인증서와 개인키

사용처 참조
  HTTPS → cert_a
```

이 상태에서 `cert_b`가 추가됐다는 이유만으로 HTTPS가 새 인증서를 사용하면 안 된다. 반대로 `cert_a`는 HTTPS가 사용하고 있으므로 삭제를 거부해야 한다. 사용처를 옮긴 뒤에도 다른 참조가 남아 있다면 삭제할 수 없다.

ONVIF 명세에서도 키·인증서·인증경로 등에 대한 참조 무결성을 요구한다. 어떤 기능이 참조 중인 객체를 삭제해 그 관계를 끊으면 안 된다는 규칙이다. [Security Service 26.06 §5.2.4](https://www.onvif.org/specs/2606/ONVIF-Security-Service-Spec-v2606.pdf)

첫 저장소의 삭제 처리는 사용처 참조와 발급자 의존성을 검사했다. 검사부터 저장 상태 변경까지 잠금 안에서 처리해 삭제 가능 여부를 확인한 직후 다른 요청이 참조를 추가하는 상황도 막았다.

이 단계에서 인증서와 개인키는 하나의 저장 객체에 묶여 있었다. 나중에 ONVIF 키 생성과 CSR을 연결하면서 키·인증서·인증경로를 독립 객체로 나눴다. 처음부터 최종 구조를 모두 구현했던 것은 아니다.

## 3. 인증서를 읽었다고 입력 전체를 저장하면 안 됐다

등록 경로를 검토하다가 PEM 처리 문제를 발견했다. PEM은 인증서나 키를 텍스트 형태로 표현하는 형식이고, 한 입력에 여러 블록이 들어갈 수 있다.

예를 들어 인증서 뒤에 개인키 블록이 붙어 있어도 인증서 파싱은 성공할 수 있다. OpenSSL의 PEM 읽기 함수는 기대한 종류가 아닌 내용을 건너뛸 수 있다. [OpenSSL PEM 함수의 Notes](https://docs.openssl.org/3.0/man3/PEM_read_bio_PrivateKey/#notes)

파싱 성공만 확인한 뒤 입력 문자열 전체를 인증서 파일로 저장하면 개인키까지 함께 저장될 수 있다. 이후 인증서 조회에서 그 문자열을 그대로 반환하면 공개해도 되는 인증서와 함께 개인키가 나간다.

등록 과정은 다음과 같이 바꿨다.

```text
입력 PEM
  → 인증서 파싱
  → 파싱한 X509 객체를 인증서 전용 PEM으로 다시 직렬화
  → 인증서 저장 및 공개 조회에 사용

개인키
  → 인증서와 키가 일치하는지 검사
  → 별도 보호 경로로 저장
```

검증한 객체에서 출력 데이터를 다시 만드는 방식이다. 공개 조회 경로에서도 인증서만 반환하는지 확인했다.

이 차이는 정상 인증서 하나를 넣는 시험으로는 잡기 어렵다. 인증서와 개인키를 함께 넣고 등록한 뒤, 디스크의 인증서 파일과 공개 조회 결과 양쪽에 개인키가 남지 않는지 검사했다.

## 4. 저장 실패 뒤에 무엇을 남길지 정했다

메모리에서 객체를 지웠더라도 디스크 저장에 실패하면 재시작 후에는 이전 객체가 다시 나타날 수 있다. 반대로 파일부터 삭제하고 목록 저장에 실패하면 목록에는 있지만 읽을 수 없는 객체가 남는다.

여기서 목록과 객체 관계를 기록하는 파일을 인덱스로 관리했다. 삭제는 인덱스 변경을 먼저 반영하고 객체 파일을 정리하는 순서로 구성했다.

```text
삭제 조건 확인
  → 인덱스 변경 준비
  → 인덱스 저장·교체
  → 삭제 대상 파일 정리
```

인덱스 교체 전에 실패하면 메모리 상태를 되돌릴 수 있다. 하지만 파일 이름을 교체한 뒤 디렉터리 동기화가 실패했다면, 변경이 영구 저장됐는지 확신할 수 없다. 이 경우에는 성공으로 응답하거나 파일을 계속 지우지 않고 저장소 사용을 중단하도록 처리했다. 다시 초기화할 때 저장 상태를 확인하게 했다.

손상된 인덱스도 빈 저장소와 구분했다. 읽기에 실패했다고 빈 목록을 만들고 나머지 파일을 정리하면, 복구할 수 있던 인증서와 키까지 잃을 수 있기 때문이다. 기존 객체가 있는데 인덱스가 없거나 잘렸다면 파일을 보존하고 초기화를 거부했다.

개인키 파일에는 암호화와 무결성 검사를 적용하고 인덱스도 무결성을 확인했다. 암호화된 파일이라는 사실만으로 객체 연결이 맞다고 볼 수는 없다. 다른 객체의 키 파일로 바꿔 넣거나 암호문의 일부를 바꾼 경우도 거부하는지 시험했다.

## 5. 첫 단계에서 어디까지 확인했나

일반 펌웨어의 컴파일·링크와 호스트 검사 97개가 통과했다. 아래는 당시 검사 출력에서 일부를 발췌한 것이다.

```text
PASS public-pem-normalized
PASS disk-certificate-has-no-private-key
PASS referenced-delete-rejected
PASS reload-persistent-state
PASS reload-references
PASS nul-index-preserves-key
PASS cross-object-key-swap-rejected
PASS uncertain-delete-defers-file-removal
RESULT PASS checks=97
```

등록과 조회의 정상 동작뿐 아니라 참조 중 삭제, 손상된 데이터, 저장 도중 실패한 경우를 함께 확인했다. 특히 삭제 요청이 실패했을 때 기존 키 파일이 남는지도 검사했다.

여기서 `reload`는 호스트 검사 안에서 저장소를 다시 초기화한 결과다. 실제 카메라 재부팅 시험은 이 단계에 포함되지 않았다. 참조 관리 검사에 TLS나 802.1X 사용처를 넣었다고 해당 프로토콜의 연결까지 검증한 것도 아니다.

첫 단계가 끝났을 때는 인증서와 키를 등록하고 ID로 조회하며 사용 중인 객체의 삭제를 막는 기반이 생겼다. 기존 인증서를 가져오는 함수도 준비했지만 nginx가 이 저장소를 실제로 사용하도록 연결하는 작업은 남아 있었다.

다음 작업은 그 연결이었다. 부팅할 때 사용할 인증서를 복원하고, 새 인증서 적용에 실패하면 기존 HTTPS 설정으로 돌아가게 만드는 과정이다. 저장소에 인증서가 정상적으로 들어 있다는 것과 웹 서버가 그 인증서로 뜬다는 것은 각각 확인해야 했다.
