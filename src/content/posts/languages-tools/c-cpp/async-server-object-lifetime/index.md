메모리를 해제하지 않았다면 누수를 의심할 수 있습니다. 그런데 이번에는 객체를 해제하는 코드가 있었습니다. 문제는 **객체가 사라진 뒤에도 다른 곳에서는 그 객체를 사용할 수 있다고 믿고 있었다는 것**이었습니다.

소유자가 객체를 해제한 시점, 관리 테이블에서 참조를 지운 시점, 서버가 실행 상태를 바꾼 시점이 맞지 않았습니다. 이를 고치려고 시작 조건을 바꿨다가, 이전 태스크가 끝나기 전에 새 태스크를 만드는 회귀도 겪었습니다.

이번 글에서는 그 과정을 바탕으로 다음 질문을 살펴보겠습니다.

> 객체를 안전하게 종료하려면, `delete` 외에 무엇을 끝내야 할까요?

아래 `Source`, `Entry`, `Framer`, `Server`는 관계를 설명하기 위해 새로 만든 이름과 예제입니다. 예제는 x86-64 Linux에서 GCC 13.3.0과 AddressSanitizer/UndefinedBehaviorSanitizer로 확인했고, 실제 장비 시험은 당시 작업 세션 기록을 바탕으로 했습니다.

## 1. 정상 응답, 프레임 수신, 프로세스 생존은 다른 사실이다

처음 문제를 좁힐 때는 “재생 실패”를 하나의 결과로 묶지 않는 것이 중요했습니다.

| 관측 | 확인할 수 있는 사실 | 바로 단정하면 안 되는 것 |
| --- | --- | --- |
| 재생 요청에 성공 응답 | 제어 요청을 수락하는 경로까지 진행됨 | 실제 프레임 생성·전송 성공 |
| 프레임 수신 없음 | 관측 구간에 기대한 데이터가 도착하지 않음 | 특정 포인터 오류가 원인이라는 결론 |
| 재생 서버 접속 실패, 웹 서버 응답 유지 | 서비스별 생존 상태가 달라짐 | 장비 전체가 즉시 멈췄다는 결론 |
| 이후 uptime 초기화 | 그 사이 재부팅이 있었음 | watchdog이 최초 원인이라는 결론 |

당시에는 재생 서버 접속 실패 후 재부팅되는 흐름이 기록됐고, watchdog 복구로 분석했습니다. 다만 보존된 근거에 watchdog 직접 로그는 없어, 그 부분은 관측 사실과 구분해야 합니다.

여기서 추적한 것은 재부팅 자체보다 앞선 문제입니다. **왜 재생에 사용하던 객체를 다시 참조했고, 왜 다음 요청이 이미 끝난 작업을 계속 사용하려 했는가?**

## 2. 객체를 소유하는 곳과 찾아 쓰는 곳이 달랐다

소유 관계를 단순화하면 다음과 같습니다. `Framer`는 원본 데이터를 감싸 프레임 단위로 다루는 래퍼라고 보면 됩니다.

```text
Session
  └─ 소유 → Framer
              └─ 소유 → Source
                          └─ 소유 → Entry

Registry[session_id] ── 비소유 참조 ──→ Entry
Entry.source        ── 비소유 참조 ──→ Source
```

`Registry`는 객체를 찾기 위한 색인입니다. 객체를 소유하지 않으므로, 테이블에 주소가 남아 있다는 사실만으로 대상의 수명이 보장되지는 않습니다.

정리해야 할 것은 세 가지였습니다.

- **소유 관계**: 누가 `Source`와 `Entry`를 파괴하는가?
- **접근 경로**: 테이블 조회나 콜백이 언제까지 그 주소를 사용할 수 있는가?
- **실행 상태**: 어떤 조건에서 서버가 “이미 재생 중”이라고 판단하는가?

이 셋이 서로 다른 함수에 나뉘어 있으면, 소멸자 하나를 읽는 것으로는 종료 처리가 맞는지 판단하기 어렵습니다.

### 2.1 래퍼의 주소와 원본의 주소는 같지 않다

실제 분석에서 중요한 단서는 **정리 함수가 받은 객체와 테이블에 기록한 객체가 같은 계층의 객체가 아니었다**는 점입니다.

테이블에는 원본 소스와 관련된 항목을 등록했는데, 종료 경로에는 원본을 감싼 프레이머가 들어왔습니다. 둘을 같은 객체라고 가정하고 주소를 비교하면 등록 항목을 찾지 못할 수 있습니다.

그 뒤 래퍼의 소멸자가 원본과 그 하위 객체를 해제하면 다음 상태가 됩니다.

```text
소유자:    Framer → Source → Entry 순서로 정리됨
테이블:    Registry[session_id]에는 예전 Entry 주소가 그대로 남음
```

이 사례에서는 래퍼 안쪽의 원본까지 확인해 등록 항목을 찾는 방향으로 수정했습니다. 일반적인 설계에서는 처음부터 등록과 해제에 같은 식별자나 등록 핸들을 사용하는 방법도 생각할 수 있습니다. 어떤 방법이든 **등록할 때의 정체성과 해제할 때의 정체성이 일치해야 한다**는 조건은 같습니다.

## 3. NULL 검사가 있어도 검사 대상이 이미 해제됐다면 늦다

중간 수정에는 항목을 지우는 대신 그 안의 소스 포인터를 비우는 접근이 있었습니다. 개념적으로 표현하면 다음과 같습니다.

```cpp
entry->source = nullptr;
// 이후 소유자가 Source와 Entry를 파괴한다.
// 하지만 Registry에는 Entry*가 남아 있다.
```

이후 사용하는 쪽에 아래 검사가 있어도 충분하지 않습니다.

```cpp
if (entry != nullptr && entry->source != nullptr) {
    // source 사용
}
```

첫 번째 조건은 포인터 값이 null인지 확인할 뿐입니다. **그 주소에 살아 있는 `Entry`가 있다는 증명은 아닙니다.**

두 번째 조건에서는 이미 `entry->source`를 읽습니다. `Entry` 자체가 해제됐다면 NULL 검사를 수행하기 위해 해제된 메모리에 접근한 셈입니다. C++의 객체 수명 규칙도 수명이 끝난 객체의 멤버 접근을 유효한 사용으로 보장하지 않습니다. [C++ 표준 초안: 객체 수명](https://eel.is/c++draft/basic.life#7)

메모리에 이전 값이 남아 우연히 문제가 드러나지 않을 수도 있습니다. 하지만 할당자가 그 공간을 재사용하는 시점에 기대어 안전성을 판단할 수는 없습니다.

이 경우 수정해야 하는 것은 검사식보다 **더 이상 유효하지 않은 항목을 조회할 수 있게 남겨 둔 구조**입니다.

## 4. 남아 있는 항목은 크래시뿐 아니라 잘못된 상태도 만들었다

테이블 항목이 남는 문제는 메모리 접근에만 영향을 주지 않았습니다.

당시 종료 경로에는 마지막 소스가 없어지면 실행 상태를 내리는 처리가 있었습니다. 아래 코드는 그 관계만 표현한 개념 예제입니다.

```cpp
if (source_table.empty()) {
    stream_started = false;
}
```

그런데 정리해야 할 항목이 계속 남아 있으면 테이블이 비지 않습니다. 소스와 태스크가 종료됐어도 서버는 “이미 시작된 스트림”으로 판단할 수 있습니다.

이 상태에서 다음 재생 요청이 들어오면 새 작업을 시작하지 않고, 기존 작업의 위치만 바꾸는 경로로 들어갑니다. 제어 응답은 성공인데 데이터를 만들 작업은 없는 상태입니다.

별도로, 태스크의 정상 종료나 생성 실패 경로에서 사용 중인 슬롯을 반납하지 않는 문제도 수정 기록에 있었습니다. 모두 “실행 중이라는 표시”와 “실제로 사용할 수 있는 작업”을 구분해야 하는 문제입니다.

### 4.1 그래서 시작 조건을 바꿨는데, 이번에는 태스크가 두 개 생겼다

처음에는 다음 판단이 자연스러워 보입니다.

> 실행 중 표시를 믿을 수 없다면, 태스크 상태를 보고 없을 때 새로 만들면 되지 않을까요?

하지만 이 수정에는 다른 전제가 필요했습니다. **태스크가 없다는 상태를 누가, 언제 확정하는가?**

당시 분석에서는 종료 요청이 공용 `running` 값을 내릴 뿐, detached 작업 스레드의 실제 종료를 기다리지 않는 구조가 확인됐습니다. 그 값을 곧바로 슬롯 재사용 조건으로 쓰면 다음 순서가 가능합니다.

| 순서 | 제어 쪽 | 이전 작업 스레드 |
| --- | --- | --- |
| 1 | `running = false`로 종료 요청 | 아직 I/O나 대기 중 |
| 2 | 비어 있는 슬롯으로 판단 | 종료 요청을 아직 확인하지 못함 |
| 3 | `running = true`, 새 작업 생성 | 아직 살아 있음 |
| 4 | 새 작업이 데이터를 공급 | 깨어나 `true`를 읽고 작업을 계속함 |

종료를 요청한 것과 종료가 완료된 것을 같은 값으로 표현한 탓입니다. 기록에는 이 변경 뒤 데이터 공급이 중복되는 증상과 서버 접속 실패가 나타났고, 해당 수정은 되돌렸습니다.

`running`을 단순히 `std::atomic<bool>`로 바꿔도 이 순서는 가능합니다. 개별 읽기·쓰기를 원자적으로 만드는 것과 **이전 작업이 끝난 뒤에만 다음 작업을 허용하는 것**은 다른 요구입니다.

### 4.2 최종 수정 지점은 시작 분기가 아니라 정리 경로였다

이 사례에서는 원본에 대응하는 테이블 항목을 올바르게 제거하자, 마지막 항목이 사라졌을 때 실행 상태를 복구하는 기존 조건도 동작했습니다. 다음 세션이 이미 끝난 작업에 접근하는 문제도 함께 해소됐습니다.

따라서 문제를 해결하기 위해 시작 분기를 계속 확장할 필요가 없었습니다. 잘못된 상태가 **어디에서 만들어졌는지**를 고치는 것이 먼저였습니다.

중복 실행을 만든 시작 조건 변경은 되돌렸고, 최종적으로 정리 경로를 수정했습니다. 종료·재사용 구조 전체를 재설계한 것은 아닙니다.

## 5. 종료 처리는 한 줄이 아니라 접근을 끝내는 절차다

이후 정리 코드를 볼 때는 `delete` 위치보다 먼저 다음 조건을 확인하게 됐습니다.

1. **새 작업을 받을 수 없게 됐는가?** 종료 중인 슬롯을 새 요청이 재사용하면 안 됩니다.
2. **기존 사용자가 접근을 끝냈는가?** 실행 중인 작업, 이미 시작된 콜백, 외부로 전달한 참조를 확인합니다.
3. **새로 찾아 들어오는 경로가 끊겼는가?** 테이블과 이벤트 등록에서 대상을 제거합니다.
4. **그 뒤 객체를 파괴하는가?** 소유권에 따라 한 번만 정리합니다.
5. **다음 요청에 보일 상태가 복구됐는가?** 슬롯, 실행 표시, 세션 연결을 함께 확인합니다.

실제 순서는 구현마다 달라질 수 있습니다. 중요한 것은 객체를 파괴하는 순간 **이미 접근 중인 사용자도 없고, 새로 접근할 경로도 없어야 한다**는 조건입니다.

### 5.1 테이블을 잠갔다고 대상 객체까지 보호되는 것은 아니다

다른 스레드가 잠금 안에서 포인터를 꺼낸 뒤, 잠금을 풀고 대상을 사용하는 구조라면 테이블에서 지우는 것만으로는 부족합니다. 이미 포인터를 받은 사용자가 있기 때문입니다.

해당 사용이 끝날 때까지 소유권을 유지하거나, 사용 종료를 확인하는 규약이 있어야 합니다. 반대로 같은 이벤트 루프에서 조회·사용·제거가 직렬로 실행되고 재진입도 없다면 더 단순한 규약을 둘 수 있습니다.

“뮤텍스가 있다”가 아니라 **그 뮤텍스가 어느 구간의 수명을 보호하는가**를 봐야 합니다.

### 5.2 종료 요청과 종료 완료를 분리한다

작업 스레드를 관리하는 구조라면 다음 상태를 구분하는 편이 명확합니다.

```text
Idle → Starting → Running → Stopping → Idle
                               종료 완료 후에만 재사용
```

이 상태 모델은 이 글에서 제안하는 설계 방향이며, 당시 코드에 그대로 구현됐다는 뜻은 아닙니다. 상태 이름을 늘리는 것만으로도 충분하지 않습니다. 각 전이를 누가 수행하고, 실패 경로에서 어디로 돌아가는지 정해야 합니다.

C++20의 `std::jthread::request_stop()`처럼 작업 쪽에 정지를 요청하는 동작과, 종료를 기다리는 `join()`은 구분됩니다. 정지 요청 자체가 스레드를 강제로 끝내는 것은 아니며, `join()`은 해당 스레드가 끝날 때까지 기다립니다. [정지 요청](https://eel.is/c++draft/thread.jthread.stop#3), [join의 의미](https://eel.is/c++draft/thread.thread.member#3)

종료 확인은 `join()`이나 완료 통지 등 구조에 맞게 구현할 수 있습니다. 단, 작업 스레드가 필요로 하는 잠금을 잡고 기다리거나, 완료 콜백을 처리해야 할 이벤트 루프를 막으면 교착을 만들 수 있습니다.

### 5.3 늦게 도착한 콜백은 다음 세션의 것도 아니다

테이블을 비운 직후 새 세션이 같은 슬롯을 쓰는 경우도 생각해야 합니다.

이전 세션의 콜백이 슬롯 번호만 가지고 뒤늦게 조회하면, 해제된 객체 대신 **새 세션의 객체**를 찾을 수 있습니다. 메모리 접근은 유효해도 잘못된 세션에 작업을 수행하는 오류입니다.

가능한 방법 중 하나는 콜백에 슬롯 번호와 세대 번호를 함께 넣고, 수명이 보장된 슬롯 관리 구조에서 현재 세대와 비교하는 것입니다. 다른 방법은 이전 콜백을 모두 취소·소진한 뒤에만 슬롯을 재사용하는 것입니다.

세대 번호도 이미 해제된 객체 안에 두고 읽으면 보호가 되지 않습니다. 아래 재현 예제는 재시작 전에 늦은 조회를 실행하는 범위까지만 다루며, 재사용 후 도착하는 이전 세션의 콜백은 구현하지 않습니다.

## 6. 작은 예제로 메모리 오류와 상태 오류를 분리해 보기

전체 서버 없이도 두 현상을 구분할 수 있습니다.

아래 예제에서 `Framer`는 `Source`를 소유하고, `Entry`는 설명을 단순화하기 위해 `Source`의 멤버로 뒀습니다. 테이블은 `Entry*`만 보관합니다.

- `uaf`: 잘못 정리한 뒤 항목을 다시 읽어 해제 후 접근을 재현합니다.
- `state`: 해제된 항목은 읽지 않고, 관리 상태가 잘못 남았는지만 확인합니다.
- `fixed`: 항목 제거 후 소유자를 해제하고, 정리·재시작을 반복합니다.

:::important
단일 슬롯과 하나의 이벤트 루프 스레드를 가정한 교육용 예제입니다. 정리 함수 안에서는 다른 콜백으로 재진입하지 않고, 콜백은 미리 저장한 포인터 대신 테이블을 다시 조회합니다.

실제 네트워크, 작업 스레드, 지연 큐는 구현하지 않았습니다. 앞 절의 스레드 중복 생성이나 멀티스레드 안전성을 재현·검증하는 코드는 아닙니다.
:::

아래 내용을 `lifetime_demo.cpp`로 저장합니다.

```cpp
#include <cassert>
#include <iostream>
#include <memory>
#include <string>
#include <unordered_map>
#include <utility>

struct Source;

struct Entry {
    Source* source;  // Non-owning: owned by the Framer.
};

struct Source {
    Entry entry{this};
    int frames = 0;
};

struct Framer {
    std::unique_ptr<Source> input = std::make_unique<Source>();
};

// One slot, one event-loop thread, no reentrant callbacks.
class Server {
public:
    void start() {
        assert(!started && table.empty() && !owner);
        auto next = std::make_unique<Framer>();
        table.emplace(1, &next->input->entry);
        owner = std::move(next);
        started = true;
    }

    void close_bad() {
        table.at(1)->source = nullptr;  // Entry itself is still registered.
        owner.reset();                // Also destroys Source::entry.
        if (table.empty()) {
            started = false;
        }
    }

    void close_good() {
        table.erase(1);  // Unregister before destroying the owner.
        owner.reset();
        started = !table.empty();
    }

    int dispatch() {
        const auto it = table.find(1);
        if (it == table.end()) {
            return 0;
        }
        Source* source = it->second->source;  // UAF after close_bad().
        return source ? ++source->frames : 0;
    }

    bool active() const { return started; }
    bool has_owner() const { return owner != nullptr; }
    std::size_t registered() const { return table.size(); }

private:
    std::unordered_map<int, Entry*> table;
    std::unique_ptr<Framer> owner;
    bool started = false;
};

int main(int argc, char** argv) {
    if (argc != 2) {
        std::cerr << "usage: lifetime_demo uaf|state|fixed\n";
        return 2;
    }

    const std::string mode = argv[1];
    Server server;

    if (mode == "uaf") {
        server.start();
        server.close_bad();
        std::cout << server.dispatch() << '\n';
    } else if (mode == "state") {
        server.start();
        server.close_bad();
        assert(!server.has_owner());
        assert(server.active() && server.registered() == 1);
        std::cout << std::boolalpha
                  << "owner=" << server.has_owner()
                  << " started=" << server.active()
                  << " entries=" << server.registered() << '\n';
    } else if (mode == "fixed") {
        for (int i = 0; i < 100; ++i) {
            server.start();
            assert(server.dispatch() == 1);
            server.close_good();
            server.close_good();  // Repeated cleanup is harmless here.
            assert(!server.has_owner() && !server.active());
            assert(server.registered() == 0);
            assert(server.dispatch() == 0);  // Late lookup finds nothing.
        }
        std::cout << "100 cycles: OK\n";
    } else {
        return 2;
    }
}
```

여기서 `close_good()`의 `started = !table.empty()`는 **이 예제의 단일 슬롯·직렬 실행 가정에서만 사용하는 상태 규칙**입니다. 실제 서버에서 테이블에 항목이 있다는 사실만으로 작업 스레드의 생존이나 프레임 공급을 판정해서는 안 됩니다.

### 6.1 AddressSanitizer를 켜고 실행하기

GCC의 `-fsanitize=address`는 해제 후 접근과 버퍼 경계 초과 같은 메모리 오류를 검사합니다. 디버그 정보와 프레임 포인터를 함께 남기면 오류 위치를 추적하는 데 도움이 됩니다. [GCC 계측 옵션](https://gcc.gnu.org/onlinedocs/gcc/Instrumentation-Options.html#index-fsanitize_003daddress)

```bash
g++ -std=c++17 -O1 -g \
  -Wall -Wextra -Wpedantic -Werror \
  -fsanitize=address,undefined -fno-omit-frame-pointer \
  lifetime_demo.cpp -o lifetime_demo

./lifetime_demo uaf
```

`uaf` 모드는 의도적으로 잘못된 메모리에 접근하므로 비정상 종료가 예상 결과입니다. 실제 실행에서 확인한 오류의 핵심은 다음과 같습니다. 주소와 전체 스택은 생략했습니다.

```text
ERROR: AddressSanitizer: heap-use-after-free
Server::dispatch()
```

보고서에서는 “접근한 위치”, “해제한 위치”, “할당한 위치”를 함께 봅니다. 마지막으로 크래시가 난 함수에 방어문을 추가하기 전에, 어떤 경로가 소유자를 파괴했고 왜 참조가 남았는지 확인하기 위해서입니다. [AddressSanitizer 보고서 예시](https://clang.llvm.org/docs/AddressSanitizer.html#symbolizing-the-reports)

### 6.2 상태가 틀렸어도 메모리 검사기는 조용할 수 있다

다음 두 모드는 각각 별도 프로세스로 실행합니다.

```bash
./lifetime_demo state
./lifetime_demo fixed
```

실행 결과는 다음과 같습니다.

```text
owner=false started=true entries=1
100 cycles: OK
```

`state` 모드는 대상 객체를 다시 읽지 않습니다. 소유자가 없는데도 실행 표시와 등록 항목이 남았다는 사실만 확인하므로, 이번 실행에서 메모리 오류 보고는 없었습니다.

이처럼 **주소를 잘못 쓰는 오류와 상태를 잘못 해석하는 오류는 검증 방법이 다릅니다.** 메모리 검사기를 통과했다고 재생 상태 전이가 맞는 것은 아닙니다.

`fixed` 모드의 100회 반복은 이 작은 예제에서 정리 후 조회, 중복 정리, 재시작을 확인한 결과입니다. 제품 전체의 안정성이나 경쟁 조건 부재를 증명하는 수치는 아닙니다.

## 7. 실제 회귀 검증에서는 무엇을 봤나

당시 기록에는 정리 경로 수정 후 재생 시나리오 6종을 10회씩 실행해, **60회에서 실패와 장비 다운이 관측되지 않은 결과**가 남아 있습니다. 이후 정리 작업을 거친 버전에서도 같은 시나리오를 5회씩 재실행한 기록이 있습니다.

중요한 것은 횟수만이 아니라 종료 순서를 바꾸어 확인한 것입니다. 예를 들어 이전 세션을 명시적으로 정리하지 않은 상태에서 새 세션을 여는 경우도 포함됐습니다.

글의 예제와 실제 서버에서 확인해야 할 항목은 다음처럼 구분할 수 있습니다.

| 조건 | 확인할 내용 |
| --- | --- |
| 정상 시작 후 종료 | 등록 항목과 실행 상태가 함께 복구되는가 |
| 작업의 자체 종료 | 클라이언트 종료 요청 없이도 참조가 정리되는가 |
| 생성 도중 실패 | 확보한 슬롯과 자원이 반납되는가 |
| 일시정지 후 재개 | 새 작업을 중복 생성하지 않는가 |
| 종료 요청 중 재시작 | 이전 작업의 종료 전 슬롯을 재사용하지 않는가 |
| 이전 콜백의 지연 도착 | 파괴된 객체나 다음 세션을 잘못 건드리지 않는가 |
| 래퍼가 있는 소스와 없는 소스 | 어느 경로에서도 같은 정리 조건이 성립하는가 |

이 표는 검토를 돕는 목록이지, 모든 항목이 해당 시험이나 작은 예제로 확인됐다는 뜻은 아닙니다. 작업 스레드 종료 대기, 생성 실패 주입, 세대가 바뀐 뒤의 콜백은 별도 시험이 필요합니다.

또한 나중에 다시 나타난 “프레임 없음” 중에는 선택한 녹화에 오디오 트랙이 없는 경우도 있었습니다. 같은 메시지가 나왔다고 방금 수정한 수명 관리 버그가 재발했다고 단정할 수는 없습니다. 상태 전이, 입력 데이터, 전송 결과를 다시 나누어 확인해야 합니다.

## 8. RAII로 소유권을 표현해도 서버의 종료 규약은 남는다

예제는 `std::unique_ptr`를 사용하지만, 잘못된 종료 경로에서는 여전히 해제 후 접근이 발생합니다. 소유자가 정확히 한 번 해제하는 것과 다른 곳의 비소유 참조를 안전하게 정리하는 것은 별개이기 때문입니다.

C++ Core Guidelines는 RAII로 자원을 관리하고, 소유 관계가 드러나도록 포인터를 사용하는 방향을 권장합니다. 이것은 출발점이지, 테이블 등록이나 비동기 작업의 종료 규약을 대신 정의해 주는 것은 아닙니다. [RAII와 자원 관리](https://isocpp.github.io/CppCoreGuidelines/CppCoreGuidelines#rr-raii), [비소유 포인터](https://isocpp.github.io/CppCoreGuidelines/CppCoreGuidelines#rr-ptr)

`shared_ptr`로 사용 중인 객체의 수명을 연장하는 설계도 가능합니다. 다만 “메모리가 살아 있다”와 “이 세션에서 새 작업을 수행해도 된다”는 여전히 다른 조건입니다. 객체를 공유 소유하게 바꾸는 것만으로 종료 상태와 슬롯 재사용 문제가 없어지지는 않습니다.

이 사례에서 얻은 기준은 다음과 같습니다.

- 객체를 누가 파괴하는지 명확히 한다.
- 비소유 참조를 어디에 등록했고 누가 제거하는지 확인한다.
- 종료 요청과 실제 종료 완료를 구분한다.
- 상태 플래그가 무엇을 뜻하며 언제 복구되는지 정의한다.
- 메모리 검사와 상태 전이 검증을 따로 수행한다.

## 9. 마무리

이 문제에서 `delete`는 빠져 있지 않았습니다. 빠져 있던 것은 **객체가 사라졌다는 사실을 그 객체를 찾고 사용하는 경로에 반영하는 일**이었습니다.

테이블 항목을 남긴 채 내부 포인터만 비우면 해제 후 접근이 남을 수 있습니다. 그 항목이 실행 상태 판단에도 쓰이면, 같은 정리 오류가 크래시와 무프레임이라는 다른 증상으로 나타날 수 있습니다.

그리고 그 결과만 보고 재시작을 허용하면, 아직 끝나지 않은 이전 작업과 새 작업이 겹칠 수도 있습니다.

그래서 지금은 종료 코드를 볼 때 이렇게 묻게 됩니다.
